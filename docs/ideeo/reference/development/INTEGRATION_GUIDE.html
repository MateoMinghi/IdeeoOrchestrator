01Qué integra esta guía

Ideeo Engine es una plataforma compartida de conversación, coordinación y ejecución autorizada. PayMe es un tenant del motor: tiene su configuración, capacidades, usuarios verificados, adaptadores bancarios y políticas. Integrar un nuevo banco no crea otro motor ni mueve su core o su ledger a esta plataforma.

Esta guía está dirigida a quienes construyen la app, el SDK, el backend del tenant y los adaptadores. Describe la implementación de desarrollo existente; los ejemplos explican formas y recorridos, no provisionan usuarios, endpoints ni permisos. La referencia de rutas se obtiene de los esquemas versionados, y los ejemplos JSON se validan con los modelos Python actuales.

02Arquitectura y responsabilidades

Contrato del motor implementado; adopción nativa pendiente. ADR-010 exige que las consultas y operaciones bancarias interactivas de app/SDK ocurran en el host. El motor interpreta; el SDK entrega la solicitud; la app abre su pantalla, autentica y usa su backend/core. Saldo y movimientos se muestran una vez allí y no vuelven al chat ni al modelo. El perfil confiable host_banking activa la entrega de intención y consumo único descrita abajo. Las pantallas y su integración con el core pertenecen a la app. Las rutas de lectura directa y enlaces siguen separadas para sus clientes configurados.

Hay dos contratos de integración diferentes: el contrato que consume el cliente y el contrato que proporciona el backend del tenant. El primero transmite conversación y resultados. El segundo permite comprobar autoridad y obtener o ejecutar acciones en el sistema de origen.

Ejemplo de un tenant: PayMe

ADR-011 confirma la separación de servicios. PayMe es solo el ejemplo de este diagrama. Otros tenants tienen su propia API, identidad, capacidades, core y arquitectura de cliente; no se les exige Armony, un WebView ni el esquema bancario de PayMe.

App/SDK → API del motor para conversación autenticada; WhatsApp → API del tenant → API del motor para mensajes que requieren IA; motor → API del tenant para servicios autorizados. En PayMe, la API del tenant encapsula Armony. El alta/KYC, las sesiones de solicitantes y los webhooks/Flows pertenecen al tenant.

  • Banca desde el chat de app/SDK: el motor infiere saldo, movimientos, transferencia u otra intención; el SDK entrega la solicitud al host, que abre su pantalla bancaria y usa su propia integración. No se consulta un core de terceros desde el motor para mostrar este saldo en chat.
  • Autorización: el host recoge la autenticación y aprobación exigidas; un «sí» escrito, un evento o un callback local no prueba una operación financiera.
  • Superagente: el motor conserva razonamiento y herramientas para tareas, con ejecutores y autoridad independientes. Otro banco delegando trabajo y un agente externo usando APIs siguen siendo interfaces distintas.
  • WhatsApp de PayMe: conserva páginas protegidas del banco para consultas/autorización. La API PayMe recibe el webhook, resuelve identidad y entrega respuestas; el motor recibe turnos autenticados. El alta/Flows y su ejecución pertenecen a PayMe.

Otros bancos y agentes

Un asistente propio de otro banco puede delegar una tarea a nuestro motor: en ese caso nuestro motor razona y devuelve seguimiento. Un agente externo puede usar APIs bancarias bajo su mandato sin usar nuestro razonamiento. Son perfiles de integración distintos. El perfil público de cliente customer descrito aquí no debe reutilizarse para suplantar esos tipos de actor.

Para el simulador de Cristobal: modela por separado la API PayMe y el core sintético. El motor debe ver el contrato del tenant configurado, sin conocer ni asumir el wire format de Harmony. Los campos y comportamientos simulados se identifican como supuestos hasta recibir el contrato oficial.

03Tu primera llamada: sandbox v1

Solo contrato de desarrollo: el saldo estructurado y replay de este sandbox no representan el flujo host-only de ADR-010. Ocultar el importe en un cliente no elimina el resultado retenido en el servidor.

Este recorrido comprueba transporte, sesión, cuenta y consumo del resultado. Usa el launcher de integración v1, de vocabulario controlado y dinero sintético. No habilita automáticamente conversación v2, onboarding o ejecución financiera. Para esas superficies usa los perfiles de las siguientes secciones.

  1. Prepara las herramientas y reserva recursos

    Desde la raíz del repositorio, usa Python 3.13, uv y las herramientas PostgreSQL 18 que exige el setup. Reserva 8230 para API y 55503 para PostgreSQL; confirma que no pertenecen a otra sesión antes de arrancar.

    uv sync --locked

  2. Prepara el fixture y arranca el servidor

    uv run python -m scripts.sdk_sandbox prepare
uv run python -m scripts.sdk_sandbox serve

    prepare crea o reutiliza el clúster local y sus registros sintéticos, aplica migraciones y preserva datos y claves existentes. El servidor usa interpretación controlada, sin llamadas pagadas al modelo.

  3. Comprueba el proceso

    curl http://127.0.0.1:8230/health/live

    La respuesta de liveness confirma que existe el proceso. No confirma disponibilidad de un banco, modelo, worker o identidad real.

  4. Instala una sesión sintética en tu terminal privada

    Ejemplo PowerShell. El archivo está ignorado por Git y contiene credenciales de cinco minutos. Nunca se publica con esta documentación.

    $sessionFile = Get-Content .runtime/sdk-sandbox/sessions.json -Raw | ConvertFrom-Json
$env:ENGINE_ACCESS_TOKEN = $sessionFile.'member-a'
$env:ENGINE_OTHER_ACCESS_TOKEN = $sessionFile.'member-b'

    Para renovar: uv run python -m scripts.sdk_sandbox sessions. Renueva también cualquier copia privada de la sesión del consumidor.

  5. Obtén las cuentas permitidas

    $headers = @{ Authorization = "Bearer $env:ENGINE_ACCESS_TOKEN" }
Invoke-RestMethod -Uri 'http://127.0.0.1:8230/v1/accounts' -Headers $headers

    Este recorrido usa PowerShell. Los ejemplos cURL de los capítulos siguientes usan sintaxis POSIX y requieren fijar sus variables en esa shell. Selecciona un account_id realmente devuelto por la API.

  6. Envía un turno con una clave estable

    $headers = @{
  Authorization = "Bearer $env:ENGINE_ACCESS_TOKEN"
  Accept = 'application/json'
  'Idempotency-Key' = 'docs-balance-001'
}
$body = @{ message = 'saldo'; account_id = 'everyday-a' } | ConvertTo-Json
Invoke-RestMethod -Uri 'http://127.0.0.1:8230/v1/turns' -Method Post -Headers $headers -ContentType 'application/json' -Body $body

    El vocabulario de este fixture incluye saldo, ¿Cuánto tengo disponible?, ¿Cuál es mi saldo? y solicitud ambigua. No es un evaluador de calidad de IA.

  7. Lee la respuesta estructurada

    Respuesta v1 de referencia · JSON validado

    La cuenta preferida del fixture tiene 1250.10 MXN. savings-a tiene 4200.00 MXN. Conserva provenance: synthetic, moneda y fecha. Los UUID del ejemplo no son los de tu ejecución.

  8. Prueba replay y conflicto

    Repite exactamente el turno, la identidad y la clave: debe recuperar el mismo resultado retenido sin otra consulta. Cambia el cuerpo con la misma clave: debe fallar por conflicto. Para obtener un saldo nuevo, crea una solicitud lógica nueva con otra clave.

  9. Ejecuta la conformidad HTTP

    uv run python scripts/contract_conformance.py --allow-inference --base-url http://127.0.0.1:8230 --fixture docs/contracts/conformance-fixture.example.json --output .runtime/sdk-http.json

    El opt-in autoriza el envío de turnos. En este sandbox específico no hay inferencia externa. El runner requiere las dos sesiones vigentes de la terminal privada.

  10. Cierra los procesos que te pertenecen

    uv run python -m scripts.sdk_sandbox stop
uv run python scripts/local_postgres.py stop

    Espera a que termine la API. Antes de un nuevo serve, retira su marcador .runtime/sdk-sandbox/stop como indica el setup. No elimines el clúster, claves ni datos para reiniciar una prueba.

Fuente operativa: ENGINE_SETUP · App/SDK integration sandbox. Las instrucciones canónicas de instalación, migraciones y recursos prevalecen sobre este resumen.

05Identidad, sesión y autorización

El tenant autentica a su cliente. El motor verifica una credencial destinada a su API y consulta autoridad vigente antes de acceder a recursos. El cuerpo del turno no puede definir tenant, usuario, scopes, agente o grant. El mismo texto enviado por dos usuarios no produce la misma identidad.

Perfil de acceso de cliente implementado

La API espera un JWT compacto ES256, header typ: at+jwt y kid registrado. El algoritmo, audiencia, issuer, firma y timestamps se validan. El perfil de desarrollo limita la vida del token a 900 segundos; el fixture genera cinco minutos. El motor no ofrece un endpoint público universal para emitir o renovar este acceso.

El SDK nunca lleva claves privadas del issuer ni API keys de modelos. Una app key, un identificador de instalación o un campo llamado tokenSAML no prueban por sí mismos una sesión bancaria válida.

Qué necesita acordar PayMe

  1. Qué flujo verifica al cliente y qué servicio emite o intercambia su credencial para el motor.
  2. Cómo se mapean membership, cliente, agente, grant, cuentas y permisos en autoridad/core.
  3. Renovación, cierre de sesión, revocación y nivel de autenticación que exige cada operación.
  4. Quién provisiona trust y claves públicas y cómo se realiza la rotación.

Esto es una integración del tenant con las interfaces existentes. La guía no elige por él un protocolo de login ni convierte todos los detalles propuestos de ADR-001 en un acuerdo de producción.

Alta ≠ sesión bancaria. Una respuesta created confirma creación según la fuente. Después, el host debe obtener el acceso de cliente y las vinculaciones de autoridad necesarias por el flujo del tenant.

Aclaraciones y seguimiento

Nuevo turno después de seleccionar una cuenta

Usa los IDs realmente recibidos. Si cambias el contenido o respondes una aclaración, genera otra clave de idempotencia. Una selección puntual de cuenta no cambia automáticamente la preferencia persistente ni el orden de fuentes de gasto de una tarjeta.

Dinero, fechas y procedencia

Los importes viajan como cadenas decimales exactas: "1250.10", junto a "MXN". En el cliente usa una librería decimal o una presentación sin cálculos de punto flotante. Un resultado synthetic debe identificarse como prueba. bank indica una fuente bancaria configurada, no una certificación o promesa de dinero de producción. Un replay conserva la observación original; no rejuvenezcas su fecha.

07Streaming, correlación y reconexión

El turno ordinario usa el mismo endpoint con Accept: text/event-stream. Recibes eventos SSE con id, event y data. El cuerpo de data se valida como AssistantEvent en v2 o TaskEvent en v1.

curl -N -X POST "$ENGINE_BASE_URL/v2/turns" \
  -H "Authorization: Bearer $ENGINE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: text/event-stream" \
  -H "Idempotency-Key: conversation-stream-001" \
  --data '{"message":"¿Cuánto tengo disponible?","account_id":"everyday-a"}'

id: 1

data: {"api_version":"2","event_id":1,"task_id":"11111111-1111-4111-8111-111111111111","type":"accepted","phase":"received","task":null}

event: progress

El evento terminal completed, failed o interrupted incluye la vista completa del turno. Progreso describe una fase de aplicación; no transmite el razonamiento privado del modelo ni prueba una operación ejecutada.

Evento terminal v2 · expandir al integrar

Reglas del consumidor

  1. Decodifica UTF-8 de forma incremental: un chunk de red no tiene por qué contener un carácter, línea o evento completo.
  2. Deduplica con (task_id, event_id). Los IDs crecen dentro de una tarea y no son globales.
  3. Comprueba que la tarea, su estado terminal y el resultado coincidan. Un duplicado con contenido distinto es un error.
  4. Finaliza el indicador de carga tanto con éxito como con error, interrupción o cierre incompleto.
  5. Al renovar sesión, hacer logout o cambiar de usuario, invalida respuestas en vuelo y limpia datos visibles y cursores del contexto anterior.

Desconectar no es cancelar todo tipo de trabajo. Los turnos ordinarios están ligados a la petición; las tareas durables tienen su propio estado y un comando de cancelación explícito. Consulta el tipo de recurso antes de asumir qué ocurre al cerrar el chat.

Qué prueba debe devolver el host

El sobre de aprobación protege términos exactos, operación, referencia y vigencia. Debe emitirse por el mecanismo confiable configurado, después del flujo de autenticación del banco. Los campos y la política real de autenticación se acuerdan con el tenant. El cliente no firma con una clave incluida en el SDK, ni manda el PIN al motor para fabricar esa prueba.

Las pruebas y permisos de desarrollo sirven para fixtures y demostraciones controladas. El servicio actual usa listeners loopback y deshabilita ejecución financiera salvo fixtures explícitamente sintéticos. No se deduce habilitación de efectos reales de que existan endpoints de execute o estructuras de permiso.

Evitar confundir tres resultados

  • Turno completo: el motor terminó de interpretar o preparar una respuesta.
  • Tarea completa: un trabajo tiene observaciones que satisfacen su objetivo bajo el contrato de esa tarea.
  • Operación bancaria completa: el banco confirmó el efecto con evidencia y vinculaciones requeridas.

La app debe mostrar el nivel que realmente conoce. Una página de banco abierta, un check local o una explicación del LLM no son recibos de pago.

Clave de idempotencia

En los turnos, Idempotency-Key tiene 1–100 caracteres de letras, dígitos, punto, guion, guion bajo y dos puntos. Una clave corresponde a una solicitud lógica bajo el mismo tenant, membership, cliente, agente y grant. Conserva clave y cuerpo para una repetición idéntica; usa otra clave para una intención nueva o una respuesta a una pregunta.

La deduplicación tiene retención acotada. El replay recupera la observación original bajo autoridad actual y no realiza una lectura bancaria fresca. La ventana de los turnos de saldo no es una garantía permanente de no repetir efectos financieros. Las operaciones y el banco deben cumplir además su contrato duradero de identidad/idempotencia.

Decidir un reintento

  1. Si conoces el ID del recurso, consulta su estado con acceso vigente.
  2. Si perdiste la respuesta de un envío, repite solo el mismo cuerpo/clave cuando el contrato de esa ruta lo permita.
  3. Si el resultado es incierto y puede haber un efecto, reconcilia con la fuente; no envíes otra compra, transferencia o creación.
  4. Un retryable: true describe una condición transitoria. No concede permiso para otra llamada pagada o efecto financiero.
  5. Si el recurso terminó con error, su replay devuelve ese error. Un nuevo intento lógico requiere decisión explícita, otra clave y los límites vigentes.

Conservación y estado local

Los defaults de desarrollo separan expiración de acceso, limpieza de contenido y marcadores mínimos de replay. Los periodos exactos y sus límites se consultan en configuración y contrato de lifecycle; no son una política universal del banco. El SDK no conserva en cachés persistentes tokens, PINs o enlaces protegidos como sustituto de una lectura autorizada.

En evidencia y soporte utiliza X-Request-ID, IDs opacos, revisión y escenario. No registres el header Bearer, assertions, PINs, cuerpos protegidos ni respuestas crudas de dependencias. Un proxy puede devolver un error no conforme a JSON; trátalo como fallo de transporte, nunca como un resultado financiero.

Ejemplo JavaScript: enviar un turno JSON y descartar una sesión anterior

Patrón ilustrativo para un cliente autorizado a llamar al origen, sin librerías externas. No es un SDK publicado ni una implementación de CORS/gateway. El token se recibe del flujo del tenant, se mantiene en memoria y se reemplaza completo al renovar.

function createConversationClient(origin) {
  let token = null;
  let generation = 0;
  const requests = new Set();

  function setSession(nextToken) {
    generation += 1;
    token = nextToken;
    for (const controller of requests) controller.abort();
    requests.clear();
    // El host también limpia mensajes sensibles, resultados y cursores visibles.
  }

  async function submit(body, idempotencyKey) {
    if (!token) throw new Error("session_required");
    const submittedGeneration = generation;
    const submittedToken = token;
    const controller = new AbortController();
    requests.add(controller);
    try {
      const response = await fetch(new URL("/v2/turns", origin), {
        method: "POST",
        credentials: "omit",
        redirect: "error",
        cache: "no-store",
        headers: {
          Authorization: `Bearer ${submittedToken}`,
          "Content-Type": "application/json",
          Accept: "application/json",
          "Idempotency-Key": idempotencyKey
        },
        body: JSON.stringify(body),
        signal: controller.signal
      });
      if (!response.headers.get("content-type")?.includes("application/json")) {
        throw new Error("unexpected_response_type");
      }
      const view = await response.json();
      if (submittedGeneration !== generation) throw new Error("session_changed");
      if (!response.ok) throw new Error(view.error?.code ?? "request_failed");
      // Validar con el esquema AssistantView antes de presentar.
      // HTTP 200 no convierte status=failed en éxito.
      return view;
    } finally {
      requests.delete(controller);
    }
  }
  return {setSession, submit};
}

No habilites credentials: include ni reenvíes cookies de otra aplicación para resolver un problema de sesión. En un navegador, usa el origen/gateway aprobado. El AbortController cancela transporte; para trabajo durable debe usarse además su comando de cancelación si esa es la intención del usuario.

20Qué queda por conectar antes de una entrega completa

Los contratos permiten comenzar la integración con fixtures. Para prometer un recorrido bancario real, el equipo debe cerrar y demostrar las siguientes fronteras; la documentación no las da por completadas.

  • Sesión de PayMe: issuer/exchange acordado, verificación del cliente, audience/trust, renovación y mapeos de agente/grant.
  • Backend del tenant: adaptación de sus APIs y semántica de cuenta/saldo, permisos y origen. Harmony oficial y el simulador son fuentes distintas.
  • Puente nativo: contrato específico de host_intent, presentación protegida, prueba de aprobación y retorno de resultado en los SDK entregados.
  • WhatsApp conversacional: API PayMe resuelve identidad y enruta turnos/resultados, con sus reglas de entrega e idempotencia. El adaptador de alta no lo sustituye.
  • Entorno accesible: URL HTTPS acordada para los dispositivos, confianza TLS y configuración. Una consola alojada no publica automáticamente la API del motor.
  • Provisionamiento real: clientes/canales, campos KYC, avisos, permisos de datos/proveedores y credenciales manejadas por sus responsables.
  • Aceptación: builds/plataformas reales, fuente de datos identificada, escenarios negativos y evidencia independiente vigente.
