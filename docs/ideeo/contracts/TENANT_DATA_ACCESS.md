# Optional tenant customer-data access

This port implements the [ownership contract](../product/DATA_OWNERSHIP_AND_LIFECYCLE.md) alongside [tenant auth](../decisions/001-tenant-authentication-and-delegation.md) and [banking ports](TENANT_BACKENDS.md). It is not a new customer login mechanism or a mandatory banking-core profile API.

`src/ai_engine/data_access.py` defines `TenantDataProvider.authorize(principal, use)` and `fetch(principal, use)` for trusted executors. A registered tenant service can map to its customer-data vault, bank service or protected user-supplied workflow. No provider is registered in the current balance runtime. Unsupported data requirements fail as `protected_data_unavailable`; the engine must not invent a customer-profile endpoint or ask a model to remember the fields.

`DataUse` names a task/resource, purpose and explicit fields. The initial vocabulary is `checkout.shipping` with recipient name/shipping address, and `invoice.billing` with recipient name/tax identifier/billing address. These are field-level task purposes, not permission to retrieve raw enrollment/KYC evidence. Unknown fields, duplicate fields and purpose/field mismatches are rejected. Adding a purpose requires its authorization, consumer and lifecycle contract; a free-form metadata object is not an extension point.

The resolver issues a random opaque reference after current authorization. References are bounded to the verified tenant, membership, client, agent account, grant, resource, purpose, fields and expiry. They contain no customer values. They are single-use, process-local, expire in at most five minutes and cannot outlive the session; restart requires reauthorization and a new reference. Capacity is bounded. Persisted long-running tasks store the intended data requirement and request a new reference on resume; they do not prolong these references or archive customer fields.

Consumption checks the entire binding, claims the reference before awaiting retrieval, rechecks current authority, requests exactly the permitted fields, validates the returned field set and rechecks authority/expiry before release. The tenant adapter must authorize resource ownership, field/purpose entitlement and current mandate from trusted records; a token scope or opaque reference alone is insufficient. A changed purpose/resource or another tenant/caller cannot consume the reference. A failed authorized consumption consumes it and requires a new authorization; no automatic retry or fallback is implied.

Values use `SecretStr` to prevent accidental representations from revealing them. They remain plaintext in trusted process memory while used; secret wrappers are not encryption or authorization. Only the approved executor/connector explicitly unwraps values for its authorized destination. Neither model-facing tool schemas nor ordinary task events expose a consume endpoint or resolved values. No wire endpoint, destination URL or customer bank credential can be selected by a model through this port. Trusted adapters must normalize errors without returning upstream bodies or secret values.

This implementation provides the enforcement primitive, not a working checkout, invoice flow or qualified tenant vault. Each actual adapter needs negative ownership/revocation/field tests, protected transport, destination policy, consent where applicable and deletion evidence before enablement.
